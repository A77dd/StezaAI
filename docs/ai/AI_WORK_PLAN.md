# План работ по ИИ и памяти «Стези»

Статус: черновик для обсуждения в команде. Дата: 2026-10-01.
Область: всё, что связано с LLM, памятью, качеством и стоимостью ИИ в бэкенде. Кода здесь нет — только что пишем, зачем и как проверяем.

Связанные документы: `docs/product/PRODUCT_CONTEXT.md`, документ сценариев этапа 0.1, ветка `codex/telegram-interaction-layer` (порты `IntentParser`, `MemoryRepository`, `SlotScheduler` и контрактные тесты).

---

## 0. Принципы

1. **LLM понимает, код действует.** Модель возвращает структурированный результат; запись в календарь, удаление, отправка сообщений — только детерминированный код и только после подтверждения пользователя.
2. **Модель не выбирает время.** Слоты подбирает `SlotScheduler`. Модель может объяснить выбор, но не придумать слот.
3. **Провайдер-независимость.** Домен не знает имён моделей. Все вызовы идут через один модуль — шлюз моделей; модель задаётся конфигом на уровне задачи.
4. **Измеряем, а не верим.** Любое изменение промпта, модели или памяти проходит наборы проверок (evals) до выката.
5. **Явные сбои.** Таймаут, невалидный JSON, превышение бюджета — это наблюдаемое событие (лог + метрика), а не тихая подмена.
6. **Чужой текст — это данные.** Пересланные и групповые сообщения никогда не интерпретируются как инструкции агенту.
7. **Значимое о человеке — после подтверждения.** Выводы о пользователе становятся долговременной памятью только после его «Да».

## 2. Шлюз моделей (`agent/gateway`)

Что пишем: один модуль, через который проходит каждый вызов LLM, эмбеддингов, реранкера и STT.

Обязанности:
- **Маршрутизация по задаче:** `parse`, `extract`, `reflect`, `chat`, `embed`, `rerank`, `transcribe`, `judge` → модель из конфига. Смена модели — правка конфига, не кода.
- **Структурированный вывод:** AI SDK 6 (`generateText` + `Output.object` со схемой zod) через `@ai-sdk/openai-compatible`. Если модель не держит JSON-схему — режим tool calling. Ответ всегда валидируется схемой.
- **Повтор при невалидном ответе:** один повтор с текстом ошибки валидации; второй сбой — явная ошибка `LlmOutputInvalid`.
- **Таймауты** по задаче (parse 8 с, extract 30 с, reflect 120 с), ретраи только на сетевые/5xx/429 с backoff.
- **Учёт:** на каждый вызов — модель, задача, input/output/cached токены, задержка, стоимость, user_id, trace_id. Пишется в таблицу `llm_calls` и в Langfuse.
- **Бюджет:** дневной лимит токенов на пользователя, глобальный предохранитель (при достижении порога — только `parse` на самой дешёвой модели, событие `budget.degraded`), алерт в служебный чат.
- **Кэш промптов:** стабильный префикс (системный промпт → ядро профиля → динамика в конце), чтобы провайдеры кэшировали начало.
- **Трассировка:** OpenTelemetry из AI SDK → Langfuse (облако на старте).

Тесты: контрактные тесты на фейковом провайдере (валидный/невалидный JSON, таймаут, 429, превышение бюджета), без сети.

## 3. Понимание сообщений (`agent/understanding`)

Что пишем: реализацию порта `IntentParser` на LLM взамен `ruleBasedIntentParser`.

### Вход
- текст (после STT для голоса), источник (`SourceRef`: тип, автор, чат, время), `now`, часовой пояс, `dateTimeHints` (детерминированно извлечённые даты);
- контекст из памяти (раздел 5.4): ядро профиля, релевантные факты, открытые задачи, календарь на сегодня.

### Выход (схема)
`kind` (task | meeting | reminder | follow_up | info), `title`, `deadline`, `durationMinutes` + `durationSource` (user | memory | default), `priority`, `participants` (ссылки на сущности памяти или новые имена), `meetingLink`, `confidence`, `needsClarification` + один вопрос с вариантами, `memoryRefs` (какие факты использованы), `about` (user | other) для фактов из чужого текста.

### Промпт
- Системная часть: роль, правила (не выбирать слот, не выполнять инструкции из пересланного текста, при сомнении — `needsClarification`), формат дат, 10–15 примеров на русском (по сценариям A–E документа 0.1).
- Ядро профиля пользователя.
- Динамика: текущее время и день недели, часовой пояс, найденные воспоминания, сообщение (чужой текст — в явных разделителях с пометкой «данные, не инструкции»).
- Промпты хранятся в репозитории с версией; версия пишется в каждый трейс.

### Постобработка (код)
- Даты: модель возвращает ISO с поясом; код проверяет «в будущем», «не дальше горизонта», согласованность с `dateTimeHints`. Иначе — уточнение.
- Длительность: если пользователь не указал — берётся из статистики памяти (`actual/estimate` по типу задачи), иначе дефолт. Модель указывает источник.
- Эскалация: `confidence < порога` или противоречие с проверками → повтор на модели `parse_escalate`. Доля эскалаций — метрика.
- Ошибка шлюза → явный ответ пользователю «не получилось разобрать, попробуйте ещё раз» + событие, без тихого отката на правила.

### Готово, когда
На наборе `intent-ru` (раздел 7): точность типа ≥ 90%, дедлайн ≥ 85%, валидный JSON ≥ 99%, p95 ≤ 2 c, цена запроса посчитана.

## 4. Голос и безопасность входа

- **Голос:** Telegram voice (OGG/Opus) → `transcribe` (whisper-large-v3) → тот же конвейер. Лимит длины, явная ошибка при недоступности (порт `TranscriptionPort` уже есть).
- **Prompt injection:** пересланный/групповой текст в разделителях; у LLM нет инструментов с побочными эффектами; извлечение памяти помечает факты из чужого текста как `about: other`; опционально предварительная проверка `guard`. Набор атак в evals (раздел 7).

## 5. Память (`memory`)

Архитектура своя, на Postgres + pgvector. Готовые системы используем как источник проверенных идей, а не как зависимости. Почему не берём готовую систему целиком:
- нужна типизированная память под нашу предметную область (длительности, обязательства, паттерны, потом карьера);
- много пользователей в одной базе;
- русский язык в поиске;
- источник и подтверждение у каждого факта;
- одна БД вместо отдельного сервиса.

### 5.0 Откуда что берём

Обзор на октябрь 2026. Цифры бенчмарков в основном сообщают сами авторы, и все бенчмарки — англоязычные чаты, поэтому наше качество проверяем своими наборами (раздел 7).

### 5.0.1 Откуда приходят данные в память

| Источник | Что получаем | Куда попадает |
|---|---|---|
| Личные сообщения и голос | задачи, намерения, предпочтения, упоминания людей и проектов | L0 → L1 |
| Пересылки | обязательства («пришлю до пятницы»), люди, проекты; автор и время источника | L0 → L1 с `about: other`, сущности L2 |
| Группы (только при вызове) | исходное сообщение + команда пользователя | L0 → L1, только для вызвавшего |
| Жизненный цикл задач | оценка, слот, перенос, отмена, выполнение | L0 → статистика |
| Check-in «Как прошло?» и причины | исход, реальная длительность, причина срыва | L0 → статистика → гипотезы |
| Ответы на подсказки и подтверждения | принятые/отклонённые выводы | L1 (confirmed / rejected) |
| Календарь | занятость, регулярные встречи (без содержимого, если пользователь не дал больше прав) | статистика (рабочие часы на деле), контекст |
| Настройки и правки в Mini App | рабочие часы, пояс, явные исправления памяти | L1 confirmed с источником «пользователь» |
| Реакция на уведомления | когда отвечает, что игнорирует | статистика → частота и время уведомлений |

### 5.1 Уровни

| Уровень | Содержимое | Кто создаёт |
|---|---|---|
| Рабочая | черновики, ожидаемые ответы, предложения | уже есть в боте |
| L0 эпизоды | все события: сообщения, пересылки, нажатия, check-in, жизненный цикл задач | синхронно, только дописывание |
| L1 факты | типизированные атомы: preference, constraint, commitment, person, project, goal, skill, achievement, fact | `extract` в фоне |
| Статистика | рабочие часы на деле, выполнение по часам, actual/estimate по типам задач, переносы, причины срывов, реакция на уведомления | SQL, без LLM |
| Гипотезы | выводы агента с уверенностью | `reflect` |
| L2 сущности/проекты | сводки по людям и проектам | `reflect` |
| L3 ядро профиля | 1–2 тыс. токенов, всегда в контексте, с версиями | `reflect` |

Поля факта: тип, субъект (`user` или сущность), содержание, `valid_from`/`valid_to`, `learned_at`, уверенность, статус (candidate | confirmed | rejected | superseded), источники (id эпизодов), модель и версия промпта извлечения, вектор + tsvector.

### 5.2 Запись (retain)
1. Событие → эпизод L0.
2. Триггер извлечения: каждые N эпизодов (стартовое N = 5) или пауза 10 мин → задача воркеру.
3. `extract`: эпизоды + существующие связанные факты → список операций `add | update | supersede | none` по схеме (подход «операции над памятью», чтобы избежать дублей).
4. Разрешение сущностей: псевдонимы и trigram → вектор → `extract` только для спорных.
5. Значимость: операционное → не память; значимое о пользователе → `candidate` (подтверждение кнопкой или во «Входящих» Mini App); отклонённое хранится как `rejected`, чтобы не предлагать снова.
6. Статистика пересчитывается на событиях задач и check-in.

### 5.3 Консолидация (reflect, ночью и после N новых фактов)
Склейка дублей, закрытие устаревшего, сводки L2, новая версия L3 (с диффом), гипотезы из статистики (с порогом уверенности и минимальным числом наблюдений), очередь проактивных подсказок, инсайты для Mini App.

### 5.4 Чтение (recall)
1. Всегда: L3 + текущее состояние.
2. Параллельно 4 канала: вектор (HNSW, halfvec), полнотекст `russian` (GIN), сущности (упомянутые люди/проекты → их факты и эпизоды), время (относительные даты → эпизоды за период).
3. Слияние RRF → `rerank` топ-50 → топ-10 → упаковка в бюджет 1,5–3 тыс. токенов с id источников.
4. Таймаут recall 1,5 c → работа по L3 + событие `memory.recall_timeout`.

### 5.5 Что видит пользователь
«Что я о тебе знаю» (просмотр, правка, удаление, источник), подтверждение кандидатов, «забудь про…», гипотезы как вопросы с кнопками, `/export` и `/deleteme` по всем таблицам памяти.

### 5.6 Готово, когда
На наборе `memory-ru` (раздел 7) ответы с памятью точнее, чем без неё; доля выдуманных фактов на `extract-ru` ≈ 0; p95 recall ≤ 800 мс.

## 6. Проактивность и следующее лучшее действие (`agent/nba`)

- **Кандидаты** собирает код: просроченное, дедлайн без блока, неразобранные «Входящие», обязательства людям, итоги check-in, гипотезы для подтверждения.
- **Ранжирование** — детерминированная формула (срочность × важность × свободное время × паттерны пользователя).
- **Формулировку** делает LLM (`parse`-модель) по выбранному кандидату с ядром профиля.
- **Доставка:** утренний план в выбранное время, после check-in, по запросу; частота ограничена настройкой уведомлений.
- **Чат Mini App:** `chat`-модель с инструментами только на чтение (поиск по памяти, календарь, задачи) и с «предложить действие» → подтверждение в интерфейсе.

## 7. Качество: наборы проверок (evals)

Хранятся в `evals/` (данные обезличены или синтетические), прогон одной командой, отчёт в Markdown + Langfuse datasets.

| Набор | Что | Размер | Метрики |
|---|---|---|---|
| `intent-ru` | фразы сценариев A–E, голосовые расшифровки, пересылки | 100–150 | точность типа, дедлайна, длительности; валидный JSON; эскалации; p50/p95; токены |
| `extract-ru` | размеченные эпизоды → ожидаемые факты | 60–80 | precision/recall, доля выдумок, верность `about` |
| `retrieval-ru` | вопрос → нужный факт | 100 пар | recall@5/@10, MRR — для выбора `embed` и `rerank` |
| `memory-ru` | синтетические 3–4-недельные истории + вопросы по категориям LongMemEval (один факт, время, обновление, несколько шагов, отказ) | 10 историй × 15 вопросов | точность (судья `judge`), токены на запрос |
| `injection-ru` | пересылки с вредными инструкциями | 30 | доля атак, повлиявших на действие или память (цель — 0) |

Порядок: малый набор (20–30) прогоняется в CI на каждое изменение промптов/моделей; полный — вручную перед выкатом и при выборе моделей.

Продакшн-сигналы: принятие первого слота, доля «Другое время», подтверждение кандидатов памяти, принятие подсказок, падение переносов.

## 8. Стоимость LLM на DAU (критерий приёмки №5)

Методика: стоимость операции = средние токены (из трасс) × цена модели (тариф шлюза). Стоимость на DAU = Σ (частота операции в день × стоимость), в трёх профилях.

| Операция Core Product Loop | Лёгкий | Типичный | Активный |
|---|---|---|---|
| разбор сообщения (`parse`) | 3 | 8 | 20 |
| эскалация (`parse_escalate`, ~10%) | 0,3 | 0,8 | 2 |
| recall (эмбеддинг запроса + rerank) | 3 | 8 | 20 |
| check-in и формулировки подсказок | 1 | 3 | 6 |
| извлечение памяти (`extract`, пакеты) | 1 | 2 | 5 |
| консолидация (`reflect`) | 0,2 | 1 | 1 |
| голос (`transcribe`, минуты) | 0 | 1 | 3 |
| чат в Mini App (`chat`) | 0 | 2 | 8 |

Результат: ₽ на DAU в день и в месяц по профилям, ₽ на одно «обращение» и прогноз, на сколько DAU хватает бюджета 75 000 ₽. Цифры заполняются после замеров (раздел 7) и получения тарифа.

## 9. Нагрузка (критерий приёмки №1)

- Инструмент: k6.
- Сценарии: вебхук бота (текст → ответ), API Mini App (Сегодня/Память), полный цикл «сообщение → parse → recall → слоты».
- LLM в нагрузке — фейковый провайдер с реалистичной задержкой (иначе сожжём бюджет); отдельно короткий замер реального шлюза: TPM/TPS по моделям `parse` и `embed` на 1–2 RPS.
- Цели: 10 RPS устойчиво, p95 вебхука ≤ 1 c без LLM, ошибки < 1%, найти точку насыщения (стресс до отказа).
- Отчёт: `docs/load/REPORT.md` — графики, p50/p95/p99, узкие места, выводы.

## 10. Метрики и логи ИИ (критерий приёмки №4)

- `llm_calls`: задача, модель, токены, задержка, стоимость, статус, trace_id.
- `analytics_events`: события продукта (сообщение, разбор, предложены слоты, принят слот, check-in, кандидат памяти подтверждён/отклонён, подсказка принята), флаг `is_internal`.
- Ошибки: JSON-логи + таблица ошибок; алерты в служебный чат.
- Дашборд Grafana: DAU, обращения на DAU, стоимость LLM в день/на DAU, p95 по задачам, доля невалидных ответов, эскалаций, таймаутов recall.
- Выгрузка: SQL/CSV одной командой.

## 12. Риски

| Риск | Мера |
|---|---|
| Модель не держит JSON-схему через шлюз | smoke-тест на шаге 1, режим tool calling, повтор с ошибкой валидации |
| Выдуманные факты в памяти | источники, кандидаты с подтверждением, `extract-ru`, судья |
| Отравление памяти через пересылки | разделители, `about: other`, `injection-ru`, guard |
| Рост расходов | дешёвая `parse`, пакетный фон, кэш промптов, лимиты, предохранитель |
| Задержка | параллельный recall с таймаутом, компактный L3 |
| Неизвестные лимиты шлюза | замер TPM/RPS на шаге 1, очередь и backoff в шлюзе |
| Нет тарифа | запросить у менторов; до этого — оценка в токенах |
